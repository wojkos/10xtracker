# See Roadmap Correlation Per Change — Plan Brief

> Full plan: `context/changes/roadmap-correlation-view/plan.md`

## What & Why

Roadmap item **S-04**: the developer should be able to see which roadmap item each change addresses, without opening `roadmap.md` and cross-referencing `change_id` by hand. This is the last piece of the "core dashboard" chain (Stream A: `F-01 → S-01 → S-02 → S-03 → S-04`) — after this, each change row shows status, phase progress, and roadmap correlation all in one place.

## Starting Point

S-01 already parses `change.md` per change folder into a status list; S-03 (just shipped) extended that with `plan.md`-derived phase progress, appended inline to the same row via `dist/app.js`'s `formatPhaseProgress()`. This change adds a third, sibling data source — the project's own `foundation/roadmap.md` — using the identical shape: new parsing module → new `ChangeSummary` field → new inline frontend suffix.

## Desired End State

Every change row that has a matching entry in its project's `roadmap.md` `## At a glance` table shows that item's roadmap ID and outcome text inline, e.g. `Some Change [implementing] — updated 2026-07-23 — Phase 2: 2/4 — S-04: see which roadmap items each change addresses`. A change with no match (no `roadmap.md`, or a `change_id` not tracked in it) shows nothing extra — no error, same as today.

## Key Decisions Made

| Decision | Choice | Why (1 sentence) | Source |
| --- | --- | --- | --- |
| What to display | Roadmap ID + outcome text, appended inline | Mirrors the exact `formatPhaseProgress()` pattern from S-03 — reuses proven rendering, no new UI structure | Plan (user-confirmed) |
| Outcome text length | Full text, no truncation | Consistent with `title` and other fields already shown untruncated on the same line | Plan |
| Multiple roadmap matches per change | Not handled as a designed case | The roadmap-generation skill guarantees unique `Change ID`s per document — this can't occur for a valid `roadmap.md` | Plan |
| Missing/malformed `roadmap.md` | Silent absence, no error field | Matches the convention `plan_progress.py` set for missing/malformed `plan.md` in S-03 | Plan |
| Parse frequency | Once per `list_changes()` call, not per change folder | The source file is project-level data, not per-change — parsing it once avoids redundant re-reads | Plan |

## Scope

**In scope:**
- New `app/roadmap_correlation.py` parsing module
- `ChangeSummary.roadmap_correlation` field, wired into `list_changes()`
- Inline frontend display in both `dist/app.js` render paths

**Out of scope:**
- Displaying `Prerequisites`, `PRD refs`, or `Status` columns from the roadmap table
- Any UI restructuring (separate badge/section) — this is a text-append, same as S-03
- Handling duplicate `Change ID`s in a malformed `roadmap.md` as a designed behavior

## Architecture / Approach

`app/roadmap_correlation.py` exposes `get_roadmap_correlations(context_dir: Path) -> dict[str, RoadmapCorrelation]`, parsing the `## At a glance` table's contiguous `|`-prefixed rows by fixed column index (ID, Change ID, Outcome — a contract enforced by the `/10x-roadmap` skill itself). `list_changes()` calls it once, then looks up each change's entry by `change_id` inside its existing per-folder loop. No `api.py` changes — the field flows through the existing `response_model`.

## Phases at a Glance

| Phase | What it delivers | Key risk |
| --- | --- | --- |
| 1. Parsing module | `get_roadmap_correlations()` parses `roadmap.md`'s table into a `change_id → (id, outcome)` dict | Table format drift from the documented contract (mitigated: contract is skill-enforced and tested against this repo's real 9-row table) |
| 2. Wire into `ChangeSummary` | `roadmap_correlation` field populated per change via one project-level parse + per-change lookup | None significant — same additive-field pattern S-03 already proved |
| 3. Frontend rendering | Roadmap ID + outcome appended inline in both render paths | Line length/crowding when phase-progress and roadmap-correlation both show (covered by manual verification) |

**Prerequisites:** S-01 (done). No new dependencies.
**Estimated effort:** ~1 session across 3 phases — same size as S-03.

## Open Risks & Assumptions

- Assumes every 10xDEV project this app points at that has a `roadmap.md` was generated by the `/10x-roadmap` skill (so the table contract holds). A hand-edited or pre-skill `roadmap.md` with a different table shape would simply show no correlations — not a crash, but worth knowing if that assumption breaks in practice.

## Success Criteria (Summary)

- Every change row with a roadmap match shows its roadmap ID + outcome text, verified against this repo's own real `roadmap.md`
- Changes without a match show nothing extra, no errors
- Refresh (`syncProject()`) keeps the roadmap-correlation text in sync, not just initial load
